# SourceWise RAG — Data Layer

## Overview

The `data/` directory houses raw source documents, test corpora, and synthetic enterprise knowledge artifacts used to validate and operate the SourceWise RAG pipeline.

As an enterprise knowledge assistant, SourceWise RAG relies on verifiable, groundable knowledge sources. Managing documentation carefully at the storage and boundary level ensures every answer generated by the system can be traced directly back to an authentic, authoritative source passage.

data/

## Source Documents vs. Processed Data

A fundamental architectural distinction exists between **raw source documents** and **processed pipeline data**:

| Property | Source Documents (`data/`) | Processed Data (Downstream Artifacts) |
| :--- | :--- | :--- |
| **State** | Raw, human-authored files (Markdown, PDF, HTML, JSON) | Normalized chunks, embeddings, vector indices |
| **Mutability** | Read-only from the pipeline's perspective; reflects original source truth | Derived dynamically; rebuildable via the ingestion pipeline |
| **Granularity** | Entire document scope (guides, wikis, runbooks) | Segmented text chunks (typically 200–800 tokens) |
| **Storage Target** | File system, object store (S3/GCS), document store | Vector database (e.g., Qdrant), embedding caches |
| **Metadata** | Author-provided frontmatter, file attributes, system tags | Enriched chunk metadata with token counts and chunk indices |

Source documents are never directly edited by the ingestion pipeline. They serve as the immutable single source of truth from which all chunks, embeddings, and vector records are derived.

## Planned Ingestion Flow

The ingestion pipeline transforms raw multi-format knowledge sources into indexed vector representations ready for semantic retrieval:

```text
Document → Extraction → Cleaning → Chunking → Embedding → Vector Index
```

1. **Document**: Source files are ingested from storage or external connectors.
2. **Extraction**: Raw text and structured frontmatter/metadata are extracted from the file format.
3. **Cleaning**: Normalization of whitespace, removal of rendering artifacts, and Unicode sanitization.
4. **Chunking**: Segmenting documents into semantically coherent, bounded chunks with configurable overlap.
5. **Embedding**: Generating dense vector representations for each text chunk using the target embedding model.
6. **Vector Index**: Upserting vector embeddings and chunk payloads into the vector store (Qdrant) with indexing on metadata fields.

## Source Traceability and Citations

SourceWise RAG enforces strict grounding: the system refuses to answer when sufficient evidence is missing, and every factual statement must be backed by a verifiable source citation.

To achieve this:
* **Unique Document Identifiers (`document_id`)**: Every ingested document carries a permanent identifier that persists across re-indexing.
* **Child Chunk Reference**: Every chunk extracted inherits its parent `document_id`, `title`, `source_path`, and `version`.
* **Citation Resolution**: When a retrieved chunk is used in generation, the citation model can reference the exact document title, file path, and chunk offset to construct user-verifiable source cards.

---

## The Role of Metadata in Retrieval

Metadata enrichment is not optional—it powers high-precision enterprise retrieval through:
* **Pre-retrieval filtering**: Restricting search scope by `product`, `department`, `source_type`, or `access_level`.
* **Recency weighting**: Utilizing `last_updated` timestamps to prioritize current policies over deprecated documentation.
* **Permission enforcement**: Respecting document `access_level` to prevent unauthorized data exposure.
* **Citation rendering**: Presenting informative context (author, version, last updated) in frontend citation dialogs.
